# Лабораторна робота №14
## Тема: Аналіз SRP/OCP у відкритих репозиторіях.
### Мета: Дослідити реалізацію принципів SRP та OCP у відкритих проєктах на C#, знайти приклади їх дотримання та порушення, а також запропонувати способи покращення структури коду.

## 1. Аналіз відкритих репозиторіїв
Для виконання роботи було обрано два відкриті проєкти на GitHub.
**ASP.NET Core** — платформа від Microsoft для створення вебзастосунків та API на C#. У проєкті використовуються інтерфейси, middleware та різні механізми розширення функціональності.
Посилання: https://github.com/dotnet/aspnetcore
**Jellyfin** — безкоштовний медіасервер із відкритим вихідним кодом. Він призначений для зберігання, організації та перегляду відео, музики й фотографій.
Посилання: https://github.com/jellyfin/jellyfin

## 2. Приклади дотримання принципу SRP
SRP (Single Responsibility Principle) — принцип єдиної відповідальності. Він означає, що клас повинен мати одну основну задачу, а його зміни мають бути пов'язані саме з цією задачею.

**Приклад 1. ASP.NET Core**
Файл: `UsePathBaseExtensions.cs`
Посилання: https://github.com/dotnet/aspnetcore/blob/main/src/Http/Http.Abstractions/src/Extensions/UsePathBaseExtensions.cs
У цьому файлі знаходиться клас `UsePathBaseExtensions`, який містить метод `UsePathBase()`. Він відповідає за додавання middleware для обробки базової частини шляху HTTP-запиту. Клас зосереджений на одній конкретній функції, тому його можна вважати прикладом дотримання SRP.

**Приклад 2. Jellyfin**
Файл: `PhotoProvider.cs`
Посилання: https://github.com/jellyfin/jellyfin/blob/master/Emby.Photos/PhotoProvider.cs
Клас `PhotoProvider` відповідає за отримання метаданих фотографій. Це видно в методі `FetchAsync()`, де зчитуються дані про камеру, дату створення, розміри зображення та інші властивості фотографії. Усі ці операції пов'язані з однією задачею — отриманням метаданих, тому клас відповідає принципу SRP.

## 3. Приклади порушення принципу SRP
**Приклад 1. Jellyfin**
Файл: `StreamingHelpers.cs`
Посилання: https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Helpers/StreamingHelpers.cs
У класі `StreamingHelpers` зібрано декілька різних операцій, пов'язаних із підготовкою потокового відтворення. Наприклад, метод `GetStreamingState()` отримує параметри HTTP-запиту, визначає потрібні кодеки та формує стан відтворення. Метод `ParseParams()` окремо розбирає параметри запиту, а `GetOutputFilePath()` формує шлях до файлу транскодування.
Це можна розглядати як порушення SRP, оскільки клас поєднує декілька різних обов'язків. Його було б зручніше розділити на окремі класи для обробки параметрів, роботи з кодеками та формування шляхів до файлів.

**Приклад 2. Jellyfin**
Файл: `ChannelManager.cs`
Посилання: https://github.com/jellyfin/jellyfin/blob/master/src/Jellyfin.LiveTv/Channels/ChannelManager.cs
Клас `ChannelManager` відповідає за керування телевізійними каналами. У ньому є методи для отримання каналів, роботи з їхніми елементами, оновлення даних, обробки медіаджерел та кешування результатів. Через таку кількість різних операцій клас має досить багато обов'язків.
Це може ускладнювати його підтримку: зміни в роботі кешу або отриманні медіаданих можуть вимагати редагування одного великого класу. Тому частину його функцій можна було б винести в окремі компоненти.

## 4. Приклади реалізації принципу OCP
OCP (Open/Closed Principle) — принцип відкритості/закритості. Він означає, що програму можна розширювати новими можливостями без необхідності змінювати вже написаний код.

**Приклад 1. ASP.NET Core**
Файл: `IApplicationBuilder.cs`
Посилання: https://github.com/dotnet/aspnetcore/blob/main/src/Http/Http.Abstractions/src/IApplicationBuilder.cs
В інтерфейсі `IApplicationBuilder` є метод `Use()`, який додає middleware до конвеєра обробки HTTP-запитів. Завдяки цьому можна підключати нові компоненти обробки запитів, не змінюючи сам інтерфейс або вже створені middleware.
Це приклад OCP, оскільки функціональність застосунку розширюється шляхом додавання нових компонентів.

**Приклад 2. Jellyfin**
Файл: `ChannelManager.cs`
Посилання: https://github.com/jellyfin/jellyfin/blob/master/src/Jellyfin.LiveTv/Channels/ChannelManager.cs
У конструкторі класу `ChannelManager` використовується `IEnumerable<IChannel> channels`. Завдяки цьому клас отримує набір реалізацій інтерфейсу `IChannel`, а не залежить від одного конкретного класу каналу.
Якщо потрібно додати новий тип каналу, можна створити новий клас, який реалізує `IChannel`, і передати його через механізм залежностей. Сам `ChannelManager` при цьому не потрібно переписувати. Це демонструє використання OCP через інтерфейси та розширення функціональності новими реалізаціями.

## 5. Пропозиція з рефакторингу
Для рефакторингу було обрано клас `StreamingHelpers` із проєкту Jellyfin, оскільки він поєднує декілька різних операцій.
Його можна розділити на три окремі компоненти. `StreamingRequestParser` відповідатиме за розбір параметрів запиту, `CodecHelper` — за перевірку та вибір кодеків, а `TranscodingPathHelper` — за формування шляхів до файлів транскодування. Основний клас `StreamingHelpers` залишиться для взаємодії між цими компонентами.
Після такого поділу кожен клас матиме чіткіше призначення. Це спростить тестування та подальші зміни: наприклад, оновлення логіки перевірки кодеків не вимагатиме редагування всього класу `StreamingHelpers`.

## Висновок
Під час лабораторної роботи було проаналізовано два відкриті репозиторії на C# — ASP.NET Core та Jellyfin. У них знайдено приклади дотримання принципу SRP, зокрема класи `UsePathBaseExtensions` і `PhotoProvider`. Також було розглянуто класи `StreamingHelpers` та `ChannelManager`, у яких можна побачити ознаки надмірної кількості обов'язків. Для принципу OCP досліджено використання middleware та інтерфейсу `IChannel`. У результаті було запропоновано розділити клас `StreamingHelpers` на декілька окремих компонентів. Робота допомогла краще зрозуміти, як принципи SRP та OCP застосовуються у реальних програмних проєктах.
